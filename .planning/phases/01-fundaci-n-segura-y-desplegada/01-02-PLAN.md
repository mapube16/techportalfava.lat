1. Generar migración vacía: `npx -w backend prisma migrate dev --create-only --name rls` y escribir el SQL A MANO (Prisma no genera ni preserva políticas):
```sql
-- daily_entries y weekly_notes: mismas 4 sentencias cada una
ALTER TABLE daily_entries ENABLE ROW LEVEL SECURITY;
ALTER TABLE daily_entries FORCE  ROW LEVEL SECURITY;   -- ni el owner miente en los tests
DROP POLICY IF EXISTS de_self ON daily_entries;        -- idempotente
CREATE POLICY de_self ON daily_entries FOR ALL TO fava_app
  USING (
    current_setting('app.is_admin', TRUE) = 'on'
    OR technician_id = NULLIF(current_setting('app.technician_id', TRUE), '')::uuid
  );
-- ídem weekly_notes con política wn_self
```
   CRÍTICO (Pitfall 3): siempre `current_setting(x, TRUE)` (missing_ok) y siempre `NULLIF(...,'')::uuid` — Postgres NO garantiza cortocircuito del OR; un admin con technician_id vacío revienta el cast sin NULLIF.
   `users` y `access_requests` NO llevan política restrictiva en esta fase: el guard hace el lookup por oid ANTES de que exista contexto RLS (fuera de la tx) — una política sobre users bloquearía el login de todos. El aislamiento de esas tablas es de capa de servicio (@Roles) hasta que una fase futura lo necesite. Dejar este razonamiento en comentario SQL.
   Aplicar con `prisma migrate dev` (el bootstrap del Plan 01 ya creó fava_app en el clúster, la shadow DB lo ve — roles son de clúster).
2. Implementar `rls.interceptor.ts` (sustituye el skeleton del Plan 01, misma clase y export — el registro en app.module no se toca):
```ts
intercept(ctx: ExecutionContext, next: CallHandler) {
  const req = ctx.switchToHttp().getRequest();
  if (!req.user) return next.handle();   // /health, estáticos, /api/me no aprovisionado
  const u = req.user;
  return from(this.prisma.base.$transaction(async (tx) => {
    await tx.$executeRaw`SELECT
      set_config('app.user_id',       ${u.id},                 TRUE),
      set_config('app.technician_id', ${u.technicianId ?? ''}, TRUE),
      set_config('app.is_admin',      ${u.roles.some((r) => r === 'A' || r === 'S') ? 'on' : 'off'}, TRUE)`;
    return als.run(tx, () => lastValueFrom(next.handle()));
  }));
}
```
   El tercer argumento TRUE de set_config es lo que evita que el contexto sobreviva al release() de la conexión del pool (anti-pattern nº1 del research). Regla escrita en comentario: NADA de I/O externo dentro de la transacción.
